CORS — derrubando o muro do navegador

Sem isso, NADA funciona — e a mensagem de erro engana o iniciante

🤔 Por que CORS existe?

Quando o front roda em
http://localhost:5173
e tenta chamar a API em
http://localhost:8080
, são
origens diferentes
(portas diferentes). Por
segurança
, o browser bloqueia chamadas cross-origin a menos que o servidor diga:
"essa origem aí pode falar comigo"
. Isso é CORS (
Cross-Origin Resource Sharing
).

Analogia: a lista do porteiro

Imagine um prédio (o backend) com porteiro. Toda visita (browser) que chega de fora, o porteiro olha numa
lista
: "esse endereço pode entrar?". Se o endereço não está na lista, ele
barra
. Configurar CORS é entregar a lista ao porteiro: "
localhost:5173
tá liberado". 🛂

📄 No
SecurityConfig.java

Java

import org.springframework.web.cors.CorsConfiguration;
import org.springframework.web.cors.CorsConfigurationSource;
import org.springframework.web.cors.UrlBasedCorsConfigurationSource;
import java.util.List;

@Bean
public CorsConfigurationSource corsConfigurationSource() {
CorsConfiguration cfg = new CorsConfiguration();
cfg.setAllowedOrigins(List.of("http://localhost:5173"));
cfg.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "OPTIONS"));
cfg.setAllowedHeaders(List.of("*"));
UrlBasedCorsConfigurationSource src = new UrlBasedCorsConfigurationSource();
src.registerCorsConfiguration("/**", cfg);
return src;
}

E no
filterChain
existente, adiciona
uma linha
:

Java

http
.cors(c -> c.configurationSource(corsConfigurationSource()))   // ← NOVO
.csrf(csrf -> csrf.disable())
.sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
// ... resto igual

A pegadinha que mata o aluno:
sem CORS, o erro no console do browser é tipo
"Access to fetch at ... has been blocked by CORS policy"
. Aluno acha que é problema no fetch/axios e fica horas debugando o front.
O problema é no back.
Sempre que ver "CORS" no console, mexa no
SecurityConfig
, não no React.

🛠️

api.js
— o coração da integração

Uma instância axios centralizada com interceptors

Antes, cada página chamava
axios.get('http://localhost:3000/fornecedores')
direto. Funcionava, mas tinha 2 problemas: (1) a URL base estava espalhada em N arquivos e (2) não tinha onde injetar o token JWT.

A solução é criar
uma instância axios única
que todas as páginas usam, e plugar nela 2
interceptors
: um que adiciona o token em cada request, outro que detecta 401 e desloga.

📄
src/services/api.js
(arquivo NOVO)

JavaScript

import axios from 'axios'

const api = axios.create({
baseURL: 'http://localhost:8080'
})

// Anexa o token JWT em cada request (se houver)
api.interceptors.request.use((config) => {
const token = localStorage.getItem('token')
if (token) {
config.headers.Authorization = `Bearer ${token}`
}
return config
})

// Trata 401 globalmente: limpa token e redireciona pro login
api.interceptors.response.use(
(response) => response,
(error) => {
if (error.response?.status === 401) {
localStorage.removeItem('token')
localStorage.removeItem('login')
if (window.location.pathname !== '/login' && window.location.pathname !== '/register') {
window.location.href = '/login'
}
}
return Promise.reject(error)
}
)

export default api

📝 Decompondo

axios.create({ baseURL: ... })
— agora você chama
api.get('/clientes')
sem repetir o domínio.

interceptors.request
— função que
roda antes de cada request sair
. Aqui adicionamos o header Authorization automaticamente.

interceptors.response
— função que
roda quando a resposta chega
. Aqui detectamos 401 e deslogamos.

localStorage
— guarda o token entre F5/abas. Survive refresh.

O
if
antes do redirect evita loop infinito quando o próprio /login devolve 401 (senha errada).

🔁 Antes × Depois nas chamadas

❌ Antes — axios direto

import axios from 'axios'

axios.get('http://localhost:3000/fornecedores')
.then(r => setFornecedores(r.data))

✅ Depois — instância api

import api from '../services/api'

api.get('/fornecedores')
.then(r => setFornecedores(r.data))

Note:
o token vai sozinho
em todo request. As páginas não precisam saber que existe autenticação. Beleza arquitetural. ✨

AuthContext
— estado global do usuário

Quem está logado? Em qualquer componente, sem prop drilling

🤔 O que é Context no React?

É a forma de
compartilhar estado
entre componentes sem passar via props. Em vez de "passar de pai pra filho pra neto pra bisneto" (prop drilling), o Context fica
acessível em qualquer lugar
da árvore.

📄
src/contexts/AuthContext.jsx
(arquivo NOVO)

JSX

import React, { createContext, useContext, useEffect, useState } from 'react'

const AuthContext = createContext(null)

export const AuthProvider = ({ children }) => {
const [login, setLogin] = useState(null)

useEffect(() => {
const savedLogin = localStorage.getItem('login')
if (savedLogin && localStorage.getItem('token')) {
setLogin(savedLogin)
}
}, [])

const signIn = (token, loginUsuario) => {
localStorage.setItem('token', token)
localStorage.setItem('login', loginUsuario)
setLogin(loginUsuario)
}

const signOut = () => {
localStorage.removeItem('token')
localStorage.removeItem('login')
setLogin(null)
}

const isAuthenticated = !!login

return (
<AuthContext.Provider value={{ login, isAuthenticated, signIn, signOut }}>
{children}
</AuthContext.Provider>
)
}

export const useAuth = () => useContext(AuthContext)

📝 Lendo o Context

createContext(null)
— cria o "container" que vai distribuir o estado.

AuthProvider
— componente que envolve a app no
App.jsx
. Tudo dentro dele consegue ler o estado.

useEffect(() => {...}, [])
— roda 1 vez quando a app carrega. Verifica se já tem token no localStorage. Isso é o que faz o
F5 não deslogar
.

signIn
/
signOut
— chamados pelas telas Login e Navbar respectivamente.

useAuth()
— hook customizado que qualquer componente usa pra pegar o estado:
const { login, isAuthenticated, signOut } = useAuth()
.

💡

Por que
localStorage
e não cookies?
Em SPA stateless com JWT, o front controla o token explicitamente — ele anexa no header. Cookies seriam enviados pelo browser automaticamente, o que
misturaria
os mundos (acidentalmente acionaria CSRF que a gente desligou no backend). Manter no localStorage é mais explícito e mais simples.

Tela de Login

Form → POST /auth/login → guarda token → redirect

O fluxo é direto. Usuário preenche, submete, recebe token, guarda no Context, e segue pra
/
.

📄
src/pages/Login.jsx
(arquivo NOVO — versão essencial)

JSX

import { useState } from 'react'
import { Card, Form, Button, Alert } from 'react-bootstrap'
import { useNavigate, Link } from 'react-router-dom'
import api from '../services/api'
import { useAuth } from '../contexts/AuthContext'

const Login = () => {
const navigate = useNavigate()
const { signIn } = useAuth()
const [login, setLogin] = useState('')
const [senha, setSenha] = useState('')
const [erro, setErro] = useState('')

const submeter = (e) => {
e.preventDefault()
setErro('')
api.post('/auth/login', { login, senha })
.then((response) => {
signIn(response.data.token, response.data.login)
navigate('/')
})
.catch((error) => {
if (error.response?.status === 401) {
setErro('Login ou senha inválidos')
} else {
setErro('Erro ao fazer login. Tente novamente.')
}
})
}

return (/* ... form com inputs e botão Entrar ... */)
}

1. Usuário digita
login
+
senha
→ clica
Entrar

2.

3. Backend valida BCrypt → devolve
{ token, login }

4.
signIn(token, login)

5.

6. Próximas requests já levam

🛡️

PrivateRoute
— rotas protegidas

Wrapper de uma linha que muda o jogo

Em React Router 7, "rota protegida" é simplesmente um componente que
verifica autenticação
antes de renderizar o filho. Se não está logado, redireciona.

📄
src/components/PrivateRoute.jsx
(arquivo NOVO)

JSX

import { Navigate } from 'react-router-dom'
import { useAuth } from '../contexts/AuthContext'

const PrivateRoute = ({ children }) => {
const { isAuthenticated } = useAuth()

if (!isAuthenticated) {
return <Navigate to="/login" replace />
}

return children
}

export default PrivateRoute

📄 Uso no
App.jsx

JSX

<Routes>
{/* Públicas */}
<Route path="/login" element={<Login />} />
<Route path="/register" element={<Register />} />

{/* Protegidas — envolvidas em PrivateRoute */}
<Route path="/" element={<PrivateRoute><Inicial /></PrivateRoute>} />
<Route path="/fornecedores" element={<PrivateRoute><Fornecedores /></PrivateRoute>} />
{/* ... resto igual ... */}
</Routes>

⚡

Defesa em camadas:
mesmo se alguém tentar acessar
/clientes
direto digitando na URL, o
PrivateRoute
redireciona. E se o cara conseguir burlar isso (impossível sem editar o JS), o
backend
ainda exige token. Front+back juntos = segurança real.

Adaptando os formulários de Fornecedor
